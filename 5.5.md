# 5.5 Redis Cluster — Distributed Redis

Until now we have understood:

- Why Redis exists
- Why Redis is in-memory
- Persistence (RDB, AOF)
- Replication
- Replication Offset
- Replication Backlog
- Full Sync
- Partial Sync
- Copy-on-Write (CoW)
- Sentinel
- Leader Election
- Replica Promotion
- Automatic Failover

At this point our Redis architecture looks like this:

```
                Clients
                   │
                   │
              Application
                   │
                   │
             ┌──────────────┐
             │ Redis Primary│
             └──────────────┘
              │     │      │
      Replication Replication Replication
              │     │      │
      ┌───────┘     │      └─────────┐
      │             │                │
 Replica A      Replica B       Replica C
```

This solves **availability**.

If Primary crashes,

Sentinel promotes one of the replicas.

Users continue using Redis.

Great.

---

But another huge problem still exists.

# The Hardware Problem

Imagine Redis stores

```
300 GB
```

of data.

Your machine has

```
128 GB RAM
```

Can Redis store

300 GB?

No.

Redis stores data in RAM.

Once RAM becomes full,

Redis cannot store additional data.

Buying a machine with

```
512 GB
```

RAM sounds simple.

But eventually

even that becomes insufficient.

Soon you'll require

```
1 TB
```

Then

```
2 TB
```

Eventually vertical scaling becomes

- expensive
- limited
- risky

There is always a hardware limit.

---

Another issue.

Suppose every second Redis receives

```
2 Million Requests/sec
```

Even if RAM is enough,

can one CPU handle this forever?

No.

CPU

Network

Memory bandwidth

NIC

everything becomes a bottleneck.

---

One more issue.

Suppose everything exists on

one Redis server.

```
300 GB
```

stored on one machine.

Every request

must go to that one server.

Even if storage is sufficient,

traffic itself becomes the bottleneck.

---

So Sentinel solved

```
Availability
```

It never solved

```
Scalability
```

---

# How can we solve this?

Simple idea.

Instead of

```
One Redis
```

Use

```
Many Redis Servers
```

Example

```
Redis A

Redis B

Redis C

Redis D
```

Now instead of storing

everything

inside one Redis,

split data.

Example

```
Users A-F

↓

Redis A

-------------------

Users G-L

↓

Redis B

-------------------

Users M-R

↓

Redis C

-------------------

Users S-Z

↓

Redis D
```

This process is called

> **Sharding (Partitioning)**

Instead of making

one machine bigger,

we distribute data across

multiple machines.

Memory

```
128 GB

+

+

+

128 GB
```

```
512 GB
```

---

Traffic

Earlier

```

↓

```

Now

```

↓

Redis A

↓

Redis B

```

Load gets distributed.

Now another question arises.

# Which Redis should store a key?

Suppose application receives

```
user:123
```

Should it go to

Redis A?

Redis C?

Redis D?

How do we decide?

We need

one deterministic rule.

The same key

must always reach

the same Redis.

Otherwise reading becomes impossible.

---

# Naive Approach

Suppose we have

4 Redis servers.

```
Hash(Key)

↓

% 4

↓

Redis
```

Example

```
Hash(user:123)

↓

14567

↓

14567 % 4

↓

3

↓

Redis D
```

Simple.

Fast.

Deterministic.

---

Problem.

Suppose tomorrow

one more Redis server is added.

Now

```
Hash(Key)

↓

% 5
```

Almost every key

moves to another server.

Example

Earlier

```
14567 % 4

↓

3
```

Now

```
14567 % 5

↓

2
```

The same key

moves.

Millions of keys change location.

This causes

massive migration.

Terrible.

---

# Consistent Hashing

This is why

Consistent Hashing was invented.

Instead of

```
Modulo
```

servers are placed

on a ring.

Keys are also hashed

onto the ring.

Each key belongs to

the first server encountered clockwise.

When a new server joins,

only nearby keys move.

Much fewer migrations happen.

---

But Redis Cluster

does **NOT**

use Consistent Hashing.

Why?

Because Redis engineers wanted

- easier management
- simpler migration
- deterministic ownership
- easier rebalancing

Instead,

they introduced

Hash Slots.

---

# Redis Hash Slots

Redis divides

the entire key space

into

```
16,384
```

logical buckets.

These buckets are called

```
Hash Slots
```

Important.

A slot

is **NOT**

memory.

It is **NOT**

a partition on disk.

It is **NOT**

a Redis server.

It is simply

a logical bucket.

Think of it like

```
Mailbox Number
```

Every key

belongs to exactly

one mailbox.

Every mailbox

belongs to exactly

one Redis server.

---

# Why exactly 16,384?

Many people think

Redis somehow calculated

this magical number.

No.

It is an engineering tradeoff.

Redis wanted

enough slots

for fine-grained balancing.

But not so many

that cluster metadata

became huge.

They chose

```
2^14

=

16384
```

Why powers of two?

Fast computations.

Compact representation.

Easy bit operations.

Small metadata.

Enough flexibility.

---

# Mapping

Suppose

```
CRC16(Key)

↓

Hash Value

↓

% 16384

↓

Slot Number
```

Example

```
user:123

↓

CRC16

↓

9021

↓

Slot 9021
```

Now

Redis Cluster checks

who owns

Slot 9021.

Suppose

```
Redis B
```

owns

```
8000-12000
```

Then

the request goes

to Redis B.

Notice something.

Application never chooses Redis.

Application only hashes the key.

The slot decides

the Redis.

---

# Slot Allocation

Suppose we have

4 Redis Masters.

Initially

all

16384

slots are allocated.

No slot remains empty.

Example

```
Redis A

0-4095

-------------------

Redis B

4096-8191

-------------------

Redis C

8192-12287

-------------------

Redis D

12288-16383
```

This is only an example.

Distribution need not be perfectly equal.

---

Important.

Slots

contain

keys.

Example

```
Slot 9200

↓

order:1

order:2

order:55

order:88
```

Redis C

owns

Slot 9200.

Therefore

every key

inside Slot 9200

physically exists

inside Redis C.

This is what

slot ownership means.

---

# New Redis Server Joins

Suppose

```
Redis E
```

is added.

Do we move

every key?

No.

Redis simply decides

which slots

Redis E

should own.

Example

Earlier

```
Redis A

0-4095
```

Now

```
Redis A

0-3000

Redis E

3001-4095
```

What happens?

Every key

belonging to

Slots

3001-4095

moves

from Redis A

to Redis E.

Notice carefully.

We never say

"Move half the memory."

We always say

"Move slots."

Because

slots determine

ownership.

Keys automatically move

with the slot.

---

# What if Redis becomes full?

Suppose

Redis B

is reaching

memory limits.

Redis Cluster

does not automatically say

```
Move Slot 6
```

Instead,

an administrator (or orchestration tooling) performs **resharding**.

Some slots from Redis B

are reassigned

to other Redis nodes.

Example

```
Before

Redis B

↓

4096-8191
```

After

```
Redis B

↓

5000-8191

Redis D

↓

4096-4999
```

Keys belonging to

4096-4999

move

to Redis D.

Load decreases.

No other slots move.

---

This fine-grained movement is exactly why Redis chose **Hash Slots** instead of assigning entire key ranges or using naive modulo hashing.

> A slot is the unit of ownership, balancing, migration, and scaling.

Understanding this one idea makes almost the entire Redis Cluster architecture intuitive.

---

# MOVED Redirection

Suppose our cluster currently looks like this.

```
Redis A

↓

Slots

0 - 4095

-------------------------

Redis B

↓

Slots

4096 - 8191

-------------------------

Redis C

↓

Slots

8192 - 12287

-------------------------

Redis D

↓

Slots

12288 - 16383
```

Suppose

```
user:123
```

hashes to

```
Slot 9200
```

Application initially sends request to

```
Redis B
```

because it still believes

Redis B owns

Slot 9200.

But earlier,

during rebalancing,

Slot 9200 had already been moved to

```
Redis C.
```

Now what?

Redis B obviously cannot process the request.

It no longer owns that slot.

Instead,

Redis B replies

```
MOVED

Slot 9200

↓

Redis C
```

Meaning

> "I no longer own this slot.
> Please update your routing information and
> talk directly to Redis C from now onwards."

Notice something important.

This is **not** an error.

It is simply informing the client that

ownership has permanently changed.

---

# What does the client do?

The client receives

```
MOVED
```

Immediately it

updates its

slot mapping.

Earlier

```
Slot 9200

↓

Redis B
```

Now

```
Slot 9200

↓

Redis C
```

Every future request

for Slot 9200

directly goes to

Redis C.

No extra redirect is required.

Therefore

MOVED generally happens

only once

per slot movement.

---

# Why cache slot mapping?

Imagine

every request

required asking

```
Which Redis owns this slot?
```

That would add

one extra network hop

for every request.

Instead,

clients maintain

a local

```
Slot → Redis
```

table.

Example

```
Slot 0-4095

↓

Redis A

----------------

4096-8191

↓

Redis B

----------------

8192-12287

↓

Redis C

----------------

12288-16383

↓

Redis D
```

Now

routing becomes

extremely fast.

Only when a MOVED occurs

does the client update

its mapping.

---

# ASK Redirection

Now consider another scenario.

Suppose Slot 9200

is currently moving

from

```
Redis B

↓

Redis C
```

Migration has started,

but not all keys

have been copied yet.

Some keys still exist in Redis B.

Some already exist in Redis C.

Migration is still

"in progress."

If Redis B immediately replies

```
MOVED
```

clients may reach Redis C,

where the requested key

doesn't exist yet.

Similarly,

some clients may still talk to Redis B.

This creates inconsistency.

Redis solves this using

```
ASK
```

---

Suppose request reaches

Redis B.

Redis B replies

```
ASK

↓

Temporarily ask Redis C.
```

Unlike MOVED,

ASK means

> "Ownership has NOT permanently changed yet.
>
> For THIS request only,
> ask Redis C."

After migration completes,

Redis starts returning

```
MOVED
```

instead.

---

## Difference

### MOVED

Permanent.

Client updates slot cache.

Future requests

go directly to new Redis.

---

### ASK

Temporary.

Migration still ongoing.

Client does NOT

update its slot table.

Only this request

is redirected.

---

This distinction is extremely important.

Interviewers often ask

Difference between

```
MOVED

vs

ASK
```

The answer is

```
MOVED

↓

Permanent ownership change

----------------------

ASK

↓

Temporary migration state
```

---

# Gossip Protocol

Now another question.

Suppose

Redis B crashes.

How do

Redis A,

Redis C,

Redis D

know about it?

Will someone maintain

one master registry?

No.

Redis Cluster uses

```
Gossip Protocol.
```

---

# Idea

Every Redis node

continuously communicates

with other Redis nodes.

Imagine

```
Redis A

↓

PING

↓

Redis C
```

Redis C replies

```
PONG
```

Along with

```
Metadata
```

Metadata includes things like

- Current Epoch
- Slot Ownership
- Node Status
- Replica Information
- Cluster Configuration

---

# Why send metadata every time?

Suppose

Redis C

knows something

that Redis A

doesn't.

Example

Redis D crashed.

Redis A still believes

Redis D is alive.

When Redis C sends

```
PONG
```

it also sends

latest metadata.

Redis A compares

both versions.

Suppose

Redis C has

newer information.

Redis A updates itself.

---

# Epoch

Every important cluster change

increments a version number.

Redis calls this

```
Configuration Epoch
```

Think of it as

```
Version Number
```

Example

```
Epoch 15
```

means

cluster state

version 15.

Later

slot migration happens.

Now

```
Epoch 16
```

Suppose another Redis

still knows

Epoch 15.

It receives

Epoch 16.

Immediately

it understands

its information

is outdated.

Newer metadata wins.

This avoids confusion

between old and new cluster layouts.

---

# How does information spread?

Students often imagine

```
Redis A

↓

broadcast

↓

Everyone
```

No.

That would create

huge network traffic.

Instead,

every Redis periodically selects

a few other nodes.

```
Redis A

↓

PING

↓

Redis C
```

Redis C responds

with metadata.

Later

Redis C

talks to Redis D.

Later

Redis D

talks to Redis B.

Eventually

new information

spreads throughout

the cluster.

Exactly like

rumours spreading

through people.

Hence the name

```
Gossip.
```

No central coordinator exists.

---

# Failure Detection

Suppose

Redis B

stops responding.

Redis A sends

```
PING
```

No response.

Redis C also

fails to receive

a response.

Redis D too.

One Redis failing

to hear from B

does NOT immediately mean

Redis B is dead.

Maybe

only the network path

between those two nodes

is broken.

Redis Cluster waits

until enough nodes

observe the same failure.

Only then

the node is considered

actually failed.

This majority-based approach

prevents false failovers.

---

# Replica Promotion

Suppose

Redis B

owns

```
Slots

4096-8191
```

and crashes.

Its replica already contains

the same data.

The cluster elects

one replica

to become

the new master.

Now

```
Slots

4096-8191
```

belong to

that promoted replica.

Clients eventually learn

the updated mapping

through Gossip,

Epoch updates

and MOVED replies.

Notice

slot ownership

does NOT change.

Only

the machine

owning those slots

changes.

This is a very important distinction.

---

# Complete Request Flow

Suppose application requests

```
user:123
```

1.

Application computes

```
CRC16(user:123)

↓

Slot Number
```

2.

Using local slot cache,

client identifies

responsible Redis.

3.

Request goes directly

to that Redis.

4.

If slot ownership changed,

Redis returns

```
MOVED
```

5.

Client updates

slot mapping.

6.

Future requests

directly reach

correct Redis.

Entire routing

requires

no central router.

No central coordinator.

Every client

knows where to go.

---

# Redis Cluster Tradeoffs

## Advantages

### Horizontal Scaling

Memory grows

by adding Redis nodes.

---

### Better Throughput

Traffic distributes

across many Redis servers.

---

### High Availability

Every master

has replicas.

Failure

doesn't stop the cluster.

---

### Fine-grained Rebalancing

Only required slots move.

Not the entire dataset.

---

### No Single Point of Failure

Routing is distributed.

Metadata is distributed.

Failure detection is distributed.

---

# Limitations

Redis Cluster

is more complex

than Sentinel.

You now have to manage

- Slot ownership
- Resharding
- Cluster metadata
- Gossip
- Replica placement
- Slot migration

Operations become

more complicated.

---

# Sentinel vs Cluster

Many engineers confuse these.

## Sentinel

Solves

```
Availability
```

It does **not**

increase memory.

It does **not**

increase throughput.

It still has

one primary.

---

## Cluster

Solves

```
Availability

+

Scalability
```

It distributes

both

storage

and

traffic.

This is why

modern production Redis deployments

almost always use

**Redis Cluster**.

Sentinel is generally chosen only when

you need automatic failover

without horizontal partitioning.

---

# Key Takeaways

Redis Cluster was introduced because

Sentinel alone cannot solve

hardware limits.

Instead of making one Redis server bigger,

Redis distributes

data into

**16,384 logical slots.**

Each slot belongs to exactly one master.

Masters can be rebalanced,

slots can migrate,

replicas provide failover,

and Gossip ensures

every node eventually learns

the latest cluster state.

This architecture allows Redis to scale

to hundreds of gigabytes of RAM,

millions of requests per second,

while still providing

automatic failover and efficient routing.
