# 5.6 Redis Data Structures

Till now we have focused on

- Redis Architecture
- Replication
- Sentinel
- Cluster
- Scaling
- Availability

Now we answer another important question.

> **How does Redis actually store different kinds of data?**

Many beginners think Redis is simply

```
Key

↓

Value
```

This is only partially correct.

Redis is actually

```
Key

↓

Data Structure
```

The data structure may be

- String
- Hash
- List
- Set
- Sorted Set
- Bitmap
- HyperLogLog
- Streams
- Geo

Every one exists because
different applications have different access patterns.

The biggest lesson throughout Redis is

> **Choose the data structure according to how the application accesses data, not according to how the entity looks.**

This philosophy appears throughout system design.

---

# Why Multiple Data Structures?

Suppose we have

```
User

↓

{
    Name
    Username
    Email
    Bio
    Followers
}
```

One may ask

> Why not simply store everything as JSON?

Technically we can.

But now suppose

```
Followers
```

changes

```
1000 times/sec
```

while

```
Bio
```

changes

once every month.

Although both belong to the same User,

their access patterns are completely different.

Storage should be designed

according to

**workload**

not according to

logical entity.

---

# Redis String

The simplest Redis data structure.

Conceptually

```
Key

↓

Value
```

Example

```
user:1:name

↓

Ujjwal
```

Another example

```
followers:user:1

↓

1200000
```

Strings are perfect for

- Counters
- Tokens
- Sessions
- OTPs
- JWT
- Cached HTML
- API Responses
- Configuration

---

# The Counter Problem

Suppose

```
followers:user:1

↓

100
```

A new follower arrives.

Naively,

application performs

```
GET

↓

100

↓

100 + 1

↓

SET 101
```

Looks correct.

Now imagine

three application servers

performing this simultaneously.

Server A

```
GET

↓

100
```

Server B

```
GET

↓

100
```

Server C

```
GET

↓

100
```

All three compute

```
101
```

Redis finally receives

```
SET 101

SET 101

SET 101
```

Final value becomes

```
101
```

instead of

```
103
```

Notice something.

Redis itself never had a race condition.

The race occurred inside

the application.

Redis simply executed

three independent SET commands.

---

# Atomic Commands

Redis solves this problem using

```
INCR

INCRBY

DECR
```

Now application sends

```
INCR followers:user:1
```

Redis internally performs

```
Read

↓

Increment

↓

Write
```

as one indivisible command.

Since Redis processes one command at a time,

no other command can observe an intermediate state.

---

## Important Observation

People often say

> Redis is single-threaded,
> therefore everything is atomic.

This is incorrect.

The correct statement is

> **Every individual Redis command is atomic.**

Example

Atomic

```
SET

GET

HSET

INCR
```

Not Atomic

```
GET

↓

Application modifies

↓

SET
```

Because another client

may execute commands

between

GET and SET.

This distinction is extremely important.

---

# Redis Hash

Suppose we want to store

```
User
```

Instead of

```
user:1:name

user:1:bio

user:1:followers
```

Redis allows

```
user:1

↓

{
    name
    username
    bio
    followers
}
```

Conceptually

```
Map<Field, Value>
```

Very similar to

```
Map<String,Object>
```

---

Perfect for

- User Profile
- Product
- Order
- Configuration
- Employee
- Customer

Any object having multiple fields.

---

# Why Hash?

Imagine storing

100 independent keys

for one user.

Managing them becomes difficult.

Instead,

Hash groups

related fields

under one logical key.

---

# Partial Updates

Suppose only

```
followers
```

changes.

Redis updates only

```
followers

↓

251
```

No need to rewrite

the complete object.

---

# Partial Reads

Suppose profile page needs only

```
Name

Username

Profile Picture
```

Redis can return

only these fields.

Instead of

sending

100 fields

over the network.

Benefits

- Less bandwidth
- Less serialization
- Less deserialization
- Lower latency

---

# Complexity

Finding a field

Average

```
O(1)
```

Updating a field

Average

```
O(1)
```

---

# Why not store Followers separately?

During discussion,

a natural question arose.

Suppose

```
Followers
```

changes

thousands of times.

Should it remain

inside Hash?

Or become

its own key?

Example

```
followers:user:1

↓

1000000
```

Both approaches are valid.

Hash lookup itself is already

```
O(1)
```

So performance

is not the deciding factor.

Instead,

the decision depends on

**access pattern.**

If follower count

has a completely different

update frequency,

TTL,

replication strategy,

or scaling requirement,

keeping it as an independent key

often makes more sense.

This is a recurring design principle.

> Data belonging to one entity
> may still be stored separately
> if its workload is different.

---

# Redis List

Suppose Instagram stores

notifications.

```
Notification 1

Notification 2

Notification 3
```

New notification arrives.

Where should it go?

Either

```
Front
```

or

```
Back
```

depending on application design.

Notice

we never search

for

```
Notification #52391
```

Instead,

operations are mostly

```
Insert

Remove

Latest N
```

Order matters.

Random lookup does not.

Redis Lists are designed exactly for this workload.

---

# Producer - Consumer Pattern

One of the biggest real-world applications of Redis Lists is

```
Queues.
```

Let us understand this from first principles.

Suppose a user signs up on our application.

After successful signup,

we need to

- Save User
- Send Welcome Email

A naive implementation would look like

```
User

↓

Signup API

↓

Save User

↓

Connect SMTP

↓

Generate Email

↓

Send Email

↓

Return Success
```

Looks fine.

But there is one problem.

Sending email may take

```
2-5 seconds.
```

Should the user wait

5 seconds

just because an email is being sent?

Obviously not.

The email is not part of the critical user flow.

The user only cares about

```
Signup Successful.
```

---

# Better Design

Instead,

Signup API performs

```
Save User

↓

Create Email Job

↓

Return Success
```

Response is returned within

```
100 ms
```

The email is sent later.

---

Now another question appears.

Who sends the email?

We introduce another process called

```
Worker
```

Architecture becomes

```
              Signup API

                   │

                   ▼

            Redis Queue

                   │

                   ▼

             Email Worker

                   │

                   ▼

             SMTP / Gmail
```

Signup API

creates work.

Worker

processes work.

This is called

```
Producer - Consumer
```

pattern.

---

# Producer

Anything which creates work.

Examples

- Signup API
- Payment Service
- Order Service
- Upload Service

---

# Consumer

Anything which performs work.

Examples

- Email Worker
- Notification Worker
- Image Compression Worker
- Invoice Generator

---

# Why Redis List?

Suppose queue contains

```
Email A

Email B

Email C
```

Worker continuously performs

```
Remove First

↓

Process

↓

Remove First

↓

Process
```

Notice something.

Nobody searches

```
Email #52391
```

Operations are only

```
Push

Pop
```

This is exactly why

Lists exist.

They are optimized for

ordered processing,

not random lookup.

---

# Queue vs Pub/Sub

Many beginners confuse these two.

They are fundamentally different.

---

## Queue

```
One Job

↓

One Worker
```

Suppose

```
Send Welcome Email
```

One worker processes it.

Job disappears.

Nobody else sees it.

---

## Pub/Sub

```
One Event

↓

Many Subscribers
```

Example

```
Order Placed
```

Inventory Service

↓

Update Stock

--------------------

Notification Service

↓

Send Notification

--------------------

Analytics Service

↓

Update Dashboard

Every subscriber receives

the same event.

Unlike Queue,

the event is

not consumed by one worker.

We will study Pub/Sub later.

---

# Redis Set

Suppose Instagram stores

```
Likes
```

One user

can like a post

only once.

Collection becomes

```
{

User A

User B

User C

}
```

Duplicates

do not make sense.

---

Another example

Followers.

```
{

Alice

Bob

Charlie

}
```

Again,

duplicates are meaningless.

---

Question.

Can Hash solve this?

Example

```
{

UserA : true

UserB : true

UserC : true

}
```

Technically,

yes.

Searching

remains

```
O(1)
```

Then why introduce

Set?

---

# Why Set Exists

Hash represents

```
Key

↓

Value
```

Set represents

```
Collection of

unique elements.
```

Semantically

these are different problems.

Redis therefore exposes

Set

as its own abstraction.

---

More importantly,

Redis can now provide

operations specific to Sets.

---

# Membership

```
Does User A exist?
```

Average

```
O(1)
```

---

# Union

Followers

Alice

```
{

A

B

C

}
```

Followers

Bob

```
{

C

D

E

}
```

Need

Everyone following

either Alice

or Bob.

```
Union
```

---

# Intersection

Need

Common followers.

```
Intersection
```

Result

```
{

C

}
```

---

# Difference

Need

People following Alice

but not Bob.

```
Difference
```

Redis directly supports

these operations.

If we used Hash,

we would implement

all of this ourselves.

---

# Important Observation

Redis Set

does not exist because

Hash cannot solve the problem.

Redis Set exists because

it represents

a richer abstraction

having operations

naturally associated

with mathematical sets.

# Redis Sorted Set (ZSET)

Normal Set

stores

```
{

A

B

C

}
```

No ordering.

Suppose we build

a gaming leaderboard.

```
Player A

↓

950

-------------------

Player B

↓

1200

-------------------

Player C

↓

800
```

Should we use Hash?

```
{

A : 950

B : 1200

C : 800

}
```

Looks reasonable.

---

Now Product Team asks

```
Show Top 100 Players.
```

Hash knows

scores.

It does not know

ranking.

Application now performs

```
Read Everything

↓

Sort

↓

Return Top 100
```

Complexity

```
O(n log n)
```

Imagine

10 Million Players.

Every leaderboard request

sorts everything.

Terrible.

---

# Better Idea

Instead of

sorting later,

keep everything

sorted

all the time.

Conceptually

```
800

↓

Player C

-------------------

950

↓

Player A

-------------------

1200

↓

Player B
```

Now

Top 100

simply means

reading

highest scores.

No sorting required.

---

# Score Update

Suppose

Player A

wins another game.

```
950

↓

1300
```

Redis roughly performs

```
Find Player

↓

Remove Old Position

↓

Insert New Position
```

Entire leaderboard

is NOT sorted again.

This is why

updates remain efficient.

---

# Internal Intuition

Conceptually,

Sorted Set combines

two ideas.

```
Hash

↓

Member → Score
```

for fast lookup.

and

```
Ordered Structure

↓

Sorted Scores
```

for fast ranking.

Do not memorize

internal implementation.

Understand

the purpose.

Redis wants

both

fast lookup

and

fast ordering.

# Real World Applications

Game Leaderboards

Top Selling Products

Ranking Systems

Priority Scheduling

Rate Limiting

Time Based Ordering

# Hash vs Sorted Set

Suppose application asks

```

```

Hash.

No ordering required.

---

Suppose application asks

```

Most Followed Creators.
```

Sorted Set.

Ordering is the entire requirement.

# Biggest Lesson

Throughout Redis,

never choose

the data structure

based on

how data looks.

Choose it

based on

how data is accessed.

Examples

User Profile

↓

Hash

-----------------------

Notifications

↓

List

-----------------------

Likes

↓

Set

-----------------------

Leaderboard

↓

Sorted Set

The entity may remain

the same.

Only the

access pattern

changes.

That determines

the correct Redis

data structure.

# Bitmap

Till now,

every Redis data structure stored

objects,

lists,

sets,

or rankings.

Now consider a completely different problem.

Suppose we have

```
100 Million Users
```

Every day,

we only want to answer

```
Did User X login today?

Yes

or

No
```

Only two possible values exist.

```
0

or

1
```

---

# Naive Solution

Store

```
user:1

↓

true

------------------

user:2

↓

false

------------------

user:3

↓

true
```

Technically,

this works.

But notice something.

We are storing

an entire Redis key

for

one bit

of information.

Every key has

metadata,

memory allocation,

internal bookkeeping,

etc.

We waste much more memory

than the actual data.

---

# Better Idea

Instead,

suppose we maintain

one huge sequence of bits.

```
101001101101001...
```

Every position

represents

one user.

Example

```
Bit 0

↓

User 0

------------------

Bit 1

↓

User 1

------------------

Bit 2

↓

User 2
```

Suppose

User 532

logs in.

Redis simply changes

```
Bit 532

↓

1
```

Need to check

whether user logged in?

Simply read

```
Bit 532
```

Memory usage becomes

extremely small.

---

# Memory Estimation

Suppose

```
100 Million Users
```

Each user requires

```
1 Bit
```

Memory required

```
100 Million Bits

≈

12.5 MB
```

Think about it.

Tracking login status

for

100 Million Users

in roughly

12.5 MB.

This is why

Bitmaps are so useful.

---

# Real Use Cases

Daily Active Users (DAU)

Monthly Active Users (MAU)

User Logged In

Feature Flags

Story Viewed

Advertisement Viewed

Email Opened

Any problem involving

```
Boolean

Yes / No
```

for

millions of users.

---

# HyperLogLog

Now another interesting problem.

Suppose

YouTube asks

```
How many unique visitors

came today?
```

Notice carefully.

They do **not** ask

who visited.

They only ask

```
Count
```

Now imagine

```
500 Million Users
```

visited today.

One approach

```
Store everyone

inside a Set.
```

Memory becomes huge.

---

But do we really need

every user?

No.

We only need

```
Unique Count
```

Redis introduces

```
HyperLogLog
```

which is

a probabilistic

data structure.

---

# What does probabilistic mean?

Suppose actual visitors are

```
10,000,000
```

HyperLogLog may return

```
9,998,420
```

or

```
10,003,115
```

Very small error.

But memory usage

remains almost constant,

irrespective of

millions of users.

---

# Tradeoff

Instead of

100% accuracy,

we sacrifice

a tiny amount of precision

to save

massive memory.

---

# Real Use Cases

Unique Visitors

Unique IP Addresses

Unique Devices

Unique Sessions

Analytics

Marketing Dashboards

Whenever

approximate count

is acceptable.

---

# Geospatial

Suppose we build

Uber.

Driver locations

continuously change.

Need to answer

```
Show Drivers

within

3 km.
```

Without

specialized indexing,

we would scan

every driver.

Impossible.

Redis provides

Geospatial indexing.

Internally,

locations are encoded

in a way

that nearby locations

remain nearby

inside Redis.

Application can now ask

```
Nearby Drivers

Nearby Restaurants

Nearby Hospitals

Nearby Delivery Partners
```

efficiently.

# Streams

Until now,

Lists provided

queues.

But Lists have limitations.

Suppose

three workers exist.

```
Worker A

Worker B

Worker C
```

Job enters queue.

Worker A

takes it.

Job disappears.

Workers B and C

never know

it existed.

This is perfect

for queues.

But what if

we want

multiple consumers,

acknowledgements,

consumer groups,

message replay,

etc.?

Redis introduces

```
Streams.
```

Think of Streams

as

an advanced,

persistent,

log-based messaging system.

Much richer

than Lists.

Still,

Streams are

far simpler

than Kafka.

---

# Queue vs Stream

Queue

```
One Job

↓

One Consumer
```

Job disappears.

---

Stream

```
Many Consumers

↓

Consumer Groups

↓

Acknowledgements

↓

Replay
```

Messages remain

until acknowledged

or deleted.

---

# Pub / Sub

Now another communication model.

Suppose

Order Service

publishes

```
Order Placed
```

Who receives it?

Inventory Service

Notification Service

Analytics Service

Fraud Detection

Every subscriber.

Architecture

```
Publisher

↓

Channel

↓

Subscribers
```

Unlike Queue,

nothing is removed.

Every subscriber

gets the same message.

---

# Pub/Sub Limitations

Redis Pub/Sub

is

fire-and-forget.

If subscriber

is offline,

message is lost.

Redis does

not

persist Pub/Sub messages.

Therefore,

Pub/Sub is useful

for

live communication,

not durable messaging.

---

# Pub/Sub vs Kafka

Kafka

stores messages.

Late consumers

can still read them.

Redis Pub/Sub

does not.

If nobody is listening,

message disappears.

Therefore,

Pub/Sub should never

replace Kafka

for durable event streaming.

---

# Memory Management

Redis stores

everything

inside RAM.

RAM

is limited.

Eventually,

memory becomes full.

Redis therefore needs

a memory management strategy.

---

# TTL

Suppose

OTP

expires after

5 minutes.

Redis stores

```
OTP

+

Expiry Time
```

Once TTL expires,

data should disappear.

---

# Lazy Expiration

Suppose

TTL expired.

But nobody accesses

that key.

Should Redis

immediately remove it?

Not necessarily.

Instead,

when someone

tries to access

that key,

Redis notices

TTL expired,

deletes it,

and returns

"Not Found."

This is called

```
Lazy Expiration.
```

Deletion happens

only when

the key is accessed.

---

# Active Expiration

What if

expired keys

are never accessed?

Memory would keep growing.

Redis therefore

periodically

checks

random keys

having TTL.

Expired keys

are deleted

in the background.

This is called

```
Active Expiration.
```

Redis uses

both

Lazy

and

Active Expiration

together.

---

# Eviction

Suppose

memory limit

has been reached.

Application still wants

to insert

new data.

Redis now needs

to remove

some existing keys.

This process is called

```
Eviction.
```

Policies include

LRU

LFU

Random

TTL-based

etc.,

which we already studied

in Chapter 5.

---

# Memory Fragmentation

Suppose

objects are

continuously

created

and deleted.

Memory develops

small unused gaps.

Even though

enough total memory exists,

large contiguous blocks

may not.

This is called

```
Memory Fragmentation.
```

Redis periodically

works with

the memory allocator

to reduce fragmentation.

---

# Final Redis Design Philosophy

Redis is

not

just

a cache.

It is

a collection

of specialized

in-memory

data structures.

Every data structure

exists because

applications

have different

access patterns.

Always choose

the data structure

according to

the query.

Not

according to

the entity.

---

# Summary

| Requirement | Redis Data Structure |
|-------------|----------------------|
| Simple Value / Counter | String |
| Object with Fields | Hash |
| Ordered Queue | List |
| Unique Collection | Set |
| Ranking / Leaderboard | Sorted Set |
| Boolean Flags | Bitmap |
| Approximate Unique Count | HyperLogLog |
| Nearby Location Search | Geospatial |
| Persistent Event Stream | Streams |

---

# Biggest Takeaway

The most important lesson from Redis is not memorizing its data structures.

The real lesson is

> **Storage should always be designed according to the application's access patterns.**

This principle extends far beyond Redis.

It applies to

- Databases
- Caching
- Indexing
- Distributed Systems
- System Design

Understanding this principle will help in designing scalable systems far more than memorizing Redis commands.
