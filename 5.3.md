# Cache Keys

Before storing anything in cache, we need a **cache key**.

The key uniquely identifies a cached response.

Without a good key, cache becomes incorrect.

Example:

```http
GET /products/123
```

Cache Key:

```
GET:/products/123
```

Next request with the same key can directly return the cached response.

---

## What should be part of a cache key?

A simple rule:

> **Everything that changes the response should affect the cache key.**

Examples:

### Request Path

```http
GET /products/123
```

≠

```http
GET /products/124
```

Different products.

Different cache keys.

---

### Query Parameters

```http
GET /products?page=1
```

≠

```http
GET /products?page=2
```

Both return different responses.

Hence query parameters become part of the cache key.

---

### Authorization (When Response Depends On User)

Example:

```http
GET /profile
```

User A

↓

Profile A

User B

↓

Profile B

If Authorization is ignored,

both users may receive the same cached response.

That is a serious security issue.

Hence whenever response depends on the user,

Authorization (or User ID) must become part of the cache key.

---

## Should every header become part of the key?

No.

Only headers that actually affect the response.

Example:

```
Accept-Language
Authorization
```

may affect the response.

Whereas:

```
Connection
User-Agent
Content-Length
```

usually do not.

Adding unnecessary fields creates many unnecessary cache entries and reduces cache hit ratio.

---

## Engineering Principle

> Cache Key should uniquely identify a response.

Not more.

Not less.

---

# Cache Consistency

One of the hardest problems in caching.

Suppose:

```
Database

↓

₹1000
```

Cache:

```
₹1000
```

User updates price.

```
₹1000 → ₹900
```

Database becomes

```
₹900
```

But cache still contains

```
₹1000
```

Now cache is stale.

---

## Why?

Because cache is only a copy.

Database remains the source of truth.

Cache and Database are two different systems.

Keeping them perfectly synchronized is difficult.

---

## Database Is Always The Source Of Truth

During our discussions we established one important principle.

Never trust cache over database.

If there is ever a conflict,

Database wins.

Always.

This principle guides every cache write strategy.

---

# Passive Consistency

Passive consistency means:

Do nothing.

Eventually cache expires.

```
TTL expires

↓

Cache Miss

↓

Database

↓

Fresh Cache
```

Simple.

Easy.

Eventually consistent.

May serve stale data for some time.

---

# Active Consistency

Instead of waiting for TTL,

application immediately tells cache:

```
Data Changed

↓

Invalidate / Update Cache
```

This reduces stale data significantly.

However,

keeping every cache layer synchronized becomes much harder.

---

## Who Should Perform Invalidation?

Application.

Not Database.

Database should only maintain data.

Application understands:

- business logic
- cache keys
- cache layers
- what needs invalidation

Hence invalidation responsibility belongs to the application.

---

## Update Cache or Delete Cache?

Suppose:

```
Update Database

↓

Update Cache
```

If cache update fails,

stale data remains.

Another approach:

```
Update Database

↓

Delete Cache
```

Next read naturally becomes

```
Cache Miss

↓

Database

↓

Fresh Cache
```

Deleting cache is often simpler and safer than updating every cached copy.

---

## Different Cache Layers Have Different Invalidation Mechanisms

Browser

- TTL
- Validation headers
- Versioned assets

CDN

- TTL
- Purge APIs
- Cache Tags

Reverse Proxy

- TTL
- Purge APIs

Application Cache

- Direct delete / update

Redis

- DEL
- Expiration
- Pub/Sub (later)

The exact mechanisms will be studied later.

For now,

remember that every layer has its own invalidation strategy.

---

# Negative Caching

Suppose user requests

```http
GET /products/999999
```

Database says

```
Product Not Found
```

Question:

Should we cache this response?

Answer:

Yes.

Reason:

Without negative caching,

every request reaches database.

```
Request

↓

Cache Miss

↓

Database

↓

"No Product"
```

Again.

Again.

Again.

Even though response never changes.

Instead,

cache

```
NO_PRODUCT
```

with a short TTL.

Future requests return directly from cache.

Database stays protected.

---

## Negative Caching Is Still Caching

Cache does not care whether response is

```
Product Object
```

or

```
No Result
```

Both are responses.

Both can be cached.

---

# Cache Policy

Does this mean we should cache every negative response?

No.

Imagine attacker sends:

```
random1

random2

random3

...

random10000000
```

If every response gets cached,

cache fills with useless entries.

Useful data gets evicted.

Memory gets wasted.

---

## Engineering Tradeoff

Negative entries usually have:

- Smaller TTL
- Normal eviction policies
- Sometimes are not cached at all
- Often combined with rate limiting

Cache is limited memory.

Not every response deserves cache space.

---

## Key Engineering Principles

- Cache only what provides value.
- Database remains the source of truth.
- Every response affecting users must have a correct cache key.
- Active consistency is harder than passive consistency.
- Cache policies are workload dependent.
- Caching "No Result" is often beneficial, but should be controlled.

# Cache Patterns

Until now we have focused on **where** cache exists.

Now we answer a different question:

> **How should an application interact with the cache?**

There is no single correct way.

Different applications have different consistency, latency and throughput requirements.

---

# 1. Cache-Aside (Lazy Loading)

The most common caching strategy.

Flow:

```
Read Request

↓

Application

↓

Cache

↓

Hit → Return

↓

Miss

↓

Database

↓

Populate Cache

↓

Return
```

Notice something important.

The cache itself does **nothing**.

The application decides:

- Check cache
- Read database
- Populate cache
- Return response

The cache simply stores key-value pairs.

It has no idea where data comes from.

---

## Why "Aside"?

Because cache sits **beside** the database.

Application knows both.

```
Application

├── Cache

└── Database
```

The cache never fetches from database on its own.

---

## Advantages

- Very simple.
- Most commonly used.
- Application has complete control.
- Works with almost every cache (Redis, Local Cache etc.)

---

## Drawbacks

Every application/service has to implement:

```
Cache Lookup

↓

Database Lookup

↓

Cache Update
```

Same logic gets repeated everywhere.

---

# 2. Read-Through Cache

Suppose cache itself knows how to fetch data.

Application simply asks:

```
Cache.get(key)
```

If cache misses,

cache itself fetches from database,

stores it,

and returns the response.

Flow:

```
Application

↓

Cache

↓

Database (if needed)

↓

Cache

↓

Application
```

---

## Difference From Cache-Aside

Cache-Aside

- Application manages cache.

Read-Through

- Cache manages itself.

---

## Advantages

- Simpler application code.
- Cache hides database interactions.

---

## Drawbacks

Cache now needs to know:

- Database
- Queries
- Serialization
- Storage logic

Cache becomes much more intelligent and tightly coupled to the database.

Business logic still belongs in the application.

Read-Through mainly removes repetitive cache handling logic.

---

# 3. Write-Through Cache

Now consider writes.

Suppose:

```
PUT /products/123

₹1000 → ₹900
```

Instead of application updating database directly,

it sends write to cache.

Flow:

```
Application

↓

Cache

↓

Database

↓

Cache Updated

↓

Success
```

User receives success only after both cache and database are updated.

---

## Why?

Suppose we updated cache first and replied immediately.

Then cache crashes before updating database.

```
Cache = ₹900

Database = ₹1000
```

Cache becomes ahead of the source of truth.

Very dangerous.

Write-Through avoids this.

---

## Advantages

- Strong consistency.
- Cache and database remain synchronized.
- Suitable where correctness is important.

Examples:

- Banking
- Financial systems
- Inventory
- Orders

---

## Drawbacks

Every write waits for database.

Higher latency.

Lower write throughput.

---

# 4. Write-Back (Write-Behind)

Some applications care more about speed than immediate consistency.

Flow:

```
Application

↓

Cache Updated

↓

Return Success

↓

Background Worker

↓

Database Updated Later
```

Notice the difference.

Database update happens asynchronously.

---

## Why?

Suppose Instagram receives

```
500,000 Likes
```

Updating database for every like is expensive.

Instead,

cache updates immediately,

then periodically flushes accumulated writes.

Example:

```
500,000 Likes

↓

Cache Counter

↓

Every few seconds

↓

One Database Update
```

Huge reduction in database writes.

---

## Suitable For

- Likes
- View Counts
- Analytics
- Metrics
- Telemetry

Data where losing a few recent updates is acceptable.

---

## Never Use For

- Banking
- Payments
- Orders
- Critical financial data

Because cache failure before database update can lose data.

---

# Engineering Principle

The choice depends on business requirements.

Consistency vs Throughput.

Correctness vs Latency.

There is no universally best write strategy.

---

# 5. Refresh-Ahead

Normally cache waits for expiry.

```
TTL expires

↓

First Request

↓

Database

↓

Cache
```

This first user pays the cache miss cost.

Instead,

application refreshes cache **before** TTL expires.

```
Cache

↓

About To Expire

↓

Background Refresh

↓

TTL Reset
```

Users continue getting cache hits.

---

## Should We Refresh Everything?

No.

Refreshing every cache entry wastes database resources.

Refresh-Ahead is useful only for:

- Frequently accessed data
- Hot Keys
- Trending content
- Popular products

Examples:

- YouTube trending videos
- Amazon best sellers
- Homepage recommendations

Not useful for rarely accessed data.

---

## Engineering Principle

Refresh-Ahead should depend on:

- Access frequency
- Popularity
- Remaining TTL

Not every cached object deserves proactive refreshing.

---

# Summary Of Cache Patterns

## Cache-Aside

Application manages cache.

Most common.

Simple.

---

## Read-Through

Cache manages database interaction.

Cleaner application code.

Smarter cache.

---

## Write-Through

Every write reaches database before success.

High consistency.

Higher latency.

---

## Write-Back

Respond quickly.

Persist later.

High throughput.

Eventually consistent.

Risk of data loss.

---

## Refresh-Ahead

Refresh important cache entries before expiry.

Avoid cache misses for hot data.

Reduce cache stampedes.

# Cache Eviction Policies

Cache memory is limited.

Eventually cache becomes full.

When a new entry arrives,

one existing entry must be removed.

This decision is made by an **Eviction Policy**.

There is no universally best policy.

Choice depends on **access patterns**, not business domain.

---

# FIFO (First In First Out)

Question it answers:

> Which cache entry has been present the longest?

Example:

```
Cache

A

B

C
```

New entry:

```
D
```

Remove:

```
A
```

because it entered first.

Result:

```
B

C

D
```

---

## Advantages

- Extremely simple.
- Cheap to implement.

---

## Drawbacks

FIFO ignores usage.

Even if A is accessed millions of times,

it can still be evicted simply because it arrived first.

---

# LRU (Least Recently Used)

Question it answers:

> Which cache entry has not been used for the longest time?

Example:

```
Cache

A

B

C
```

Access pattern:

```
A

C

A

A
```

Insert:

```
D
```

Remove:

```
B
```

because it hasn't been accessed recently.

---

## Why LRU Works

Most applications exhibit **Temporal Locality**.

If data was accessed recently,

it is likely to be accessed again soon.

Examples:

- Currently viewed products
- Trending videos
- Active user sessions
- Recently opened documents

---

## Drawback

A frequently used object may temporarily become inactive.

LRU may evict it,

even though it is generally popular.

---

# LFU (Least Frequently Used)

Question it answers:

> Which cache entry has been used the least?

Example:

```
A : 1000 Requests

B : 3 Requests

C : 15 Requests
```

Insert:

```
D
```

Remove:

```
B
```

because it has the lowest frequency.

---

## Why LFU Works

Some data remains popular for a long time.

Examples:

- Frequently downloaded files
- Popular static assets
- Frequently accessed configuration

LFU preserves these objects.

---

## Drawback

Old popular objects may remain in cache forever,

even if nobody accesses them anymore.

---

# Engineering Principle

No eviction policy is perfect.

Choose according to access patterns.

| Policy | Best For | Weakness |
|----------|----------|----------|
| FIFO | Simplicity | Ignores usage |
| LRU | Recently accessed data | Misses long-term popularity |
| LFU | Frequently accessed data | Old popular entries may remain forever |

---

# Cache Failure Modes

Caching introduces new problems.

Understanding these failures is more important than memorizing terminology.

---

# Cache Penetration

Suppose requests are made for data that does not exist.

Example:

```
GET /products/999999999
```

Cache:

```
Miss
```

Database:

```
No Product
```

If millions of such requests arrive,

every request bypasses cache and reaches database.

```
Cache

↓

Miss

↓

Database

↓

No Result
```

Database gets overloaded,

even though cache is working correctly.

---

## Mitigation

- Negative Caching
- Short TTL
- Request Validation
- Rate Limiting
- Firewall / IDS / IPS

(Later we will study Bloom Filters.)

---

# Cache Breakdown (Hot Key Breakdown)

Suppose a very popular cache entry expires.

```
Product 123

↓

100,000 Requests/sec
```

TTL expires.

Suddenly:

```
100,000 Cache Misses

↓

Database
```

One hot key causes a massive spike on the database.

---

## Mitigation

### Request Coordination

Only one request fetches data.

Remaining requests wait.

```
100,000 Requests

↓

One DB Query

↓

Cache Updated

↓

Remaining Requests Read Cache
```

This is the **FETCHING** state discussed in Chapter 5.1.

---

### Refresh-Ahead

Refresh important cache entries before TTL expires.

Users never experience the cache miss.

---

### Longer TTL

Frequently accessed data often deserves longer TTLs.

---

# Cache Avalanche

Different from Cache Breakdown.

Here,

many cache entries expire together.

Example:

```
1 Million Cache Entries

TTL = 1 Hour
```

Exactly after one hour,

all entries expire.

Thousands of unrelated requests now hit the database simultaneously.

---

## Mitigation

### Natural Staggering

If cache entries are created over time,

their expiry times naturally differ.

---

### TTL Jitter (Randomized TTL)

Instead of:

```
TTL = 3600 seconds
```

Assign:

```
3600 ± Random Offset
```

Example:

```
Product A

3612 sec

Product B

3748 sec

Product C

3524 sec
```

Now cache entries expire gradually,

preventing sudden database spikes.

---

# Engineering Takeaways

Caching is never just about storing data.

Every caching decision involves tradeoffs.

Questions every engineer should ask:

- Does this response deserve cache space?
- How should the cache key be designed?
- Can stale data be tolerated?
- Should cache be updated or invalidated?
- Which cache pattern best fits the business?
- Which eviction policy matches access patterns?
- What happens if cache fails?
- What happens when TTL expires?
- How is the database protected during cache failures?

Caching is ultimately a balance between:

- Performance
- Freshness
- Consistency
- Memory
- Cost
- Operational Complexity

There is no perfect cache.

There is only the cache strategy that best matches the application's requirements.
