# Chapter 5.4 — Redis: The Distributed Cache (Part 1)

---

# Why Redis?

Before learning Redis, let's first understand **why it even exists**.

A common mistake developers make is learning Redis as a technology first.

Instead, let's derive it from the problem.

---

# The Problem with Application-Level Cache

Suppose we have a simple application.

```text
                Users
                  │
                  ▼
           Application Server
                  │
                  ▼
               MySQL
```

Every request reaches the application.

The application asks MySQL.

MySQL returns the result.

Everything works.

---

Now imagine a product page.

```
GET /product/123
```

Thousands of users request the same product.

The flow becomes:

```text
Users
   │
   ▼
Application
   │
   ▼
MySQL
```

Every request reaches the database.

Even though **all users are asking for exactly the same data**.

This is wasteful.

The database repeatedly performs the same work.

---

Instead, the application can remember the response.

```text
User

↓

Application

↓

Cache?

↓

Database
```

If the product is already present in memory,

there is absolutely no need to ask the database again.

---

The request now becomes:

```text
Users
   │
   ▼
Application
   │
   ├────────► Cache
   │              │
   │         Cache Hit
   │              │
   ▼              ▼
Return Response  Database Not Touched
```

Latency becomes much smaller.

Database load decreases.

Overall throughput increases.

---

This is called an **Application Cache**.

---

# Why Doesn't Application Cache Scale?

Everything works perfectly.

Then the company grows.

Instead of one application server,

we now have:

```text
                    Load Balancer
                    /          \
                   /            \
                  ▼              ▼

             App Server 1    App Server 2
                    │              │
                    └──────┬───────┘
                           │
                           ▼
                         MySQL
```

Each application server now has its own memory.

Suppose:

```
GET /product/123
```

First request reaches:

```
App Server 1
```

Cache miss.

Database is queried.

Cache is populated.

Everything is good.

---

Now another request arrives.

Load Balancer sends it to:

```
App Server 2
```

Problem.

App Server 2 has **no idea** what App Server 1 cached.

It again queries MySQL.

Again caches locally.

---

Now imagine:

100 application servers.

Each one stores:

```
product:123
```

independently.

We now have:

100 copies

of

the exact same data.

---

# Problems with Application Cache

## 1. Duplicate Memory

Suppose each cache entry occupies:

```
1 MB
```

100 servers.

```
100 × 1 MB

=

100 MB
```

Only one copy was actually required.

The remaining 99 MB is duplicated.

As systems grow,

this becomes an enormous waste of RAM.

---

## 2. Cache Invalidation

Suppose the product price changes.

Old value:

```
₹999
```

New value:

```
₹899
```

Now ask yourself.

How many caches need updating?

Every application server.

If there are:

```
100 servers
```

then

```
100 cache entries
```

must be updated or invalidated.

Keeping all application caches synchronized becomes increasingly difficult.

---

## 3. Load Balancer Doesn't Know Where Cache Exists

The Load Balancer only balances traffic.

It does **not** know where a particular cache entry resides.

It simply forwards requests.

Example:

```text
                Load Balancer

                 /        \

               App1      App2

              (Hit)      (Miss)
```

A request may reach the server that has the cache.

Or it may not.

The Load Balancer has no awareness of cache locality.

---

## 4. Poor Cache Utilization

Imagine:

App Server 1

contains:

```
product:123
```

App Server 2

contains:

```
product:456
```

Both servers have free memory.

Yet neither can use the other's cache.

Memory becomes fragmented across machines.

---

# The Better Architecture

Instead of giving every application server its own cache,

let's separate the cache.

```text
                 Load Balancer

                       │

        ┌──────────────┴──────────────┐

        ▼                             ▼

   App Server 1                  App Server 2

        │                             │

        └──────────────┬──────────────┘

                       │

                       ▼

                Central Cache

                       │

                       ▼

                     MySQL
```

Now all application servers share one cache.

---

Advantages:

- Single copy of data
- Easier invalidation
- Better memory utilization
- Independent scaling
- Centralized cache management

This is called a **Distributed Cache**.

---

# Why Not Use MySQL as Cache?

Many beginners ask:

> "If we're already storing data in MySQL, why not just optimize MySQL?"

Good question.

Because the database and cache solve different problems.

---

Databases provide:

- Durability
- Transactions
- Constraints
- ACID guarantees
- Disk persistence
- Complex queries
- Joins
- Indexes

These guarantees are expensive.

Every read and write performs a lot of work.

---

A cache has a completely different objective.

Its goal is simply:

> Return data as quickly as possible.

It sacrifices many database guarantees to achieve extremely low latency.

---

# Why Not Build Another Application?

Another question.

Instead of Redis,

why not build another Java or Node.js application?

```
GET key

↓

Return value
```

Wouldn't that work?

Technically,

yes.

But it wouldn't be nearly as efficient.

Because:

- A general-purpose application executes business logic.
- Runs garbage collection.
- Parses requests.
- Handles routing.
- Uses frameworks.

Redis does almost none of that.

Redis is built specifically for one purpose:

> Extremely fast in-memory data access.

Every design decision inside Redis optimizes for this goal.

---

# Redis

Redis is an **in-memory data structure store**.

The important words are:

**In-memory**

Everything is primarily stored in RAM.

Not on disk.

---

Simplified architecture:

```text
Application

↓

Redis

↓

RAM
```

No disk access is required during normal reads.

Memory latency is dramatically lower than disk latency.

This is why Redis is so fast.

---

# Why RAM is Fast

Suppose your application asks for:

```
product:123
```

If Redis has it,

the CPU can retrieve it directly from memory.

No disk seek.

No spinning disk.

No SSD lookup.

No filesystem traversal.

Just memory access.

This reduces latency from milliseconds to microseconds.

---

# Why Isn't Everything Stored in RAM?

If RAM is so fast,

why don't databases store everything in RAM?

Because RAM has tradeoffs.

---

## Tradeoff 1 — Cost

RAM is significantly more expensive than SSDs or HDDs.

Storing terabytes of data entirely in RAM becomes economically impractical.

---

## Tradeoff 2 — Capacity

Servers usually have much less RAM than disk storage.

Example:

```
RAM

256 GB

Disk

10 TB
```

Huge datasets cannot fit entirely into memory.

---

## Tradeoff 3 — Volatility

RAM is volatile.

If power is lost,

memory disappears.

Everything stored only in RAM is lost.

---

# Does That Mean Redis Loses Everything?

Initially,

yes.

If Redis only stored data in RAM,

then after a crash:

```text
Power Failure

↓

RAM Cleared

↓

Redis Empty
```

Clearly,

this is unacceptable for many applications.

So Redis introduced:

**Persistence**

---

# Why Persistence?

Persistence means:

> Periodically save the contents of RAM onto disk.

Now,

if Redis crashes,

it can rebuild itself from disk.

Without persistence:

```text
Redis Crash

↓

Everything Lost
```

With persistence:

```text
Redis Crash

↓

Read Saved Data

↓

Restore Memory

↓

Continue Serving Requests
```

Redis provides two persistence mechanisms.

1. RDB (Redis Database Snapshot)
2. AOF (Append Only File)

These solve the same problem differently.

# Chapter 5.4 — Redis: The Distributed Cache (Part 2)

---

# Persistence

In the previous section we learned that Redis primarily stores data in RAM.

RAM provides extremely low latency.

However, RAM is volatile.

If the Redis process crashes or the machine loses power,

everything in memory disappears.

To solve this problem, Redis introduces **Persistence**.

Persistence simply means:

> Save enough information on disk so that Redis can rebuild itself after a restart.

Redis provides two persistence mechanisms.

1. RDB (Redis Database Snapshot)
2. AOF (Append Only File)

Each solves the same problem differently.

---

# RDB (Redis Database Snapshot)

The idea behind RDB is very straightforward.

Instead of saving every write,

Redis periodically captures a **complete snapshot** of its memory.

Imagine Redis currently contains:

```text
user:1

user:2

product:10

likes:55
```

At some configured interval,

Redis creates a snapshot.

```text
RAM

↓

Snapshot

↓

dump.rdb
```

Now suppose Redis crashes.

Instead of starting empty,

it performs:

```text
Read dump.rdb

↓

Rebuild Memory

↓

Ready
```

The entire dataset comes back.

---

# Advantages of RDB

## 1. Fast Recovery

Instead of replaying millions of operations,

Redis simply loads one snapshot.

Recovery is usually very fast.

---

## 2. Compact Backup

A snapshot stores only the final state.

It does not contain every write operation.

This makes RDB files relatively compact.

---

## 3. Good for Backups

If you want nightly backups,

RDB is an excellent option.

You can even copy the snapshot to another server.

---

# Problem with RDB

Suppose Redis creates snapshots every:

```
5 minutes
```

Timeline:

```text
12:00

Snapshot Created

↓

12:01

User Likes Post

↓

12:02

Another User Likes Post

↓

12:03

Redis Crashes
```

Question:

Will those likes exist after restart?

No.

Redis only has the snapshot from:

```
12:00
```

Everything between:

```
12:00

↓

12:03
```

is lost.

---

This means RDB can lose recent data.

Whether this is acceptable depends entirely on the business.

---

# Is RDB Always Bad?

No.

Suppose you're caching:

- Product Catalog
- Movie Details
- Public User Profiles

Losing a few minutes of cache is acceptable.

The cache can even be rebuilt from MySQL.

In such systems,

RDB is often sufficient.

---

# AOF (Append Only File)

Instead of periodically storing snapshots,

AOF records every write operation.

Example:

```text
SET user:1 "Ujjwal"

SET product:10 "iPhone"

DEL session:45

INCR likes
```

Redis simply appends these operations to a file.

```text
Append Only File

↓

SET ...

SET ...

DEL ...

INCR ...
```

Nothing complicated.

Just a continuously growing log.

---

# Crash Recovery using AOF

Suppose Redis crashes.

Instead of loading one snapshot,

Redis performs:

```text
Read First Command

Execute

↓

Read Second Command

Execute

↓

Read Third Command

Execute

↓

Continue...
```

Eventually,

memory reaches exactly the same state it had before the crash.

---

# Advantages of AOF

## 1. Better Durability

Since every write is recorded,

data loss is much smaller.

Depending on configuration,

Redis may lose only a second (or even less) of writes.

---

## 2. Accurate Recovery

Redis rebuilds itself by replaying the exact sequence of operations.

The final state matches the state before the crash.

---

# Problem with AOF

Imagine:

```
SET likes 1

INCR likes

INCR likes

INCR likes

INCR likes
```

The final value is:

```
5
```

But AOF still contains:

```
SET

INCR

INCR

INCR

INCR
```

After millions of operations,

the log becomes huge.

Recovery also becomes slower because Redis must replay every operation.

---

# RDB vs AOF

RDB stores:

> State

AOF stores:

> History

---

Think about them like this.

RDB:

```text
Take Photo

↓

Restore Photo
```

AOF:

```text
Watch Entire Movie Again

↓

Reach Current State
```

One stores the destination.

The other stores the journey.

---

# Which One is Better?

There is no universal answer.

It depends on the business.

---

Suppose you're building Instagram.

If Redis crashes,

losing a few seconds of cache is acceptable.

The cache can be rebuilt.

RDB may be sufficient.

---

Suppose Redis is storing critical session information.

You want minimal data loss.

AOF becomes much more attractive.

---

Suppose you're building a banking system.

Even losing one second of financial data is unacceptable.

In such systems,

Redis usually isn't treated as the source of truth at all.

The database remains the ultimate authority.

If Redis disappears,

the application rebuilds cache from the database.

---

# The Best Approach

Many production systems don't choose one.

They use both.

---

Imagine:

```text
Every Few Minutes

↓

Create RDB Snapshot
```

Meanwhile:

```text
Every Write

↓

Append to AOF
```

Suppose Redis crashes.

Recovery becomes:

```text
Load Latest Snapshot

↓

Replay Remaining AOF Entries

↓

Current State Restored
```

Instead of replaying millions of operations,

Redis only replays operations after the latest snapshot.

This provides:

- Faster startup
- Lower data loss
- Smaller recovery time

This is why combining RDB and AOF is common in production.

---

# Why Replication?

Persistence protects against crashes.

But another problem still exists.

Suppose Redis itself dies.

```text
Application

↓

Redis

↓

Crash
```

Even if persistence exists,

Redis needs time to restart.

During that time,

applications cannot read cache.

We need High Availability.

---

The simplest solution is replication.

```text
          Primary Redis

               │

        ┌──────┴──────┐

        ▼             ▼

   Replica 1     Replica 2
```

The Primary accepts writes.

Replicas continuously copy its data.

---

# Why Only One Primary?

Imagine both machines accepted writes.

```text
Redis A

SET Likes = 100

Redis B

SET Likes = 99
```

Which value is correct?

Conflict.

To avoid conflicts,

Redis uses:

One Primary

Multiple Replicas

---

# Read Flow

Write:

```text
Application

↓

Primary
```

Read:

```text
Application

↓

Primary

or

Replica
```

Now read requests are distributed.

Read throughput increases significantly.

---

# Replication

Whenever the Primary executes:

```
SET product:10
```

It immediately executes the operation locally.

Then sends the same operation to every Replica.

```text
Primary

↓

SET Product

↓

Replica 1

↓

Replica 2
```

Eventually,

all replicas become identical.

---

# Synchronous vs Asynchronous Replication

Imagine:

Primary receives:

```
SET likes 100
```

Two possibilities exist.

---

## Synchronous

```text
Primary

↓

Replica Updated

↓

Client Receives Success
```

Advantage:

Replicas are always consistent.

Problem:

Every client waits for every replica.

Latency increases.

If a replica is slow,

the entire write becomes slow.

---

## Asynchronous

```text
Primary

↓

Respond to Client

↓

Replicate in Background
```

Client receives success immediately.

Replication happens independently.

Latency becomes much lower.

---

This is what Redis primarily uses.

Asynchronous replication.

---

# Tradeoff

Asynchronous replication introduces one risk.

Suppose:

```text
Primary

↓

Client Gets Success

↓

Primary Crashes

↓

Replica Never Received Update
```

The newest write disappears.

This is the tradeoff.

Redis chooses performance over perfect consistency.

For a cache,

this is usually acceptable.

---

# Why Replication Helps

Replication provides:

- High Availability
- Read Scaling
- Disaster Recovery
- Backup Node
- Reduced Read Load

It does **not** increase write throughput.

Every write still reaches one Primary.

---

# Production Observation

Many beginners think:

```
3 Replicas

=

3x Write Performance
```

Wrong.

Replication improves:

Reads.

Not Writes.

Because there is still only one Primary accepting modifications.

# Chapter 5.4 — Redis: The Distributed Cache (Part 3)

---

# Replication Offset

In the previous section, we saw that the Primary continuously sends every write operation to all Replicas.

A natural question arises.

How does Redis know **how much data a Replica has already received?**

At first glance, you might think:

> "Why not just count the number of commands?"

Unfortunately, that doesn't work well.

---

# Why Not Count Commands?

Suppose the replication stream is:

```text
SET x 10

SET user:1 {5 KB JSON}

DEL session:15

INCR likes
```

Now imagine the network disconnects while sending the second command.

```text
SET user:1 {5 KB JSON}
                ^
        Connection Lost
```

Has the Replica received:

- 1 command?
- 2 commands?

Neither.

It has received **part of the second command**.

Counting commands cannot precisely describe where replication stopped.

---

Another example.

```text
SET x 10
```

may occupy

```
10 Bytes
```

while

```text
SET hugeJSON {20 MB}
```

occupies

```
20 MB
```

Both are one command.

Clearly, counting commands doesn't represent the amount of replicated data.

---

# Replication Offset

Redis instead keeps a continuously increasing **byte counter**.

Imagine the replication stream.

```text
SET A

SET B

DEL C

INCR D
```

Suppose:

```
SET A

20 Bytes
```

Offset becomes

```
20
```

Next command

```
30 Bytes
```

Offset becomes

```
50
```

Next command

```
15 Bytes
```

Offset becomes

```
65
```

The Primary now says:

```
Current Replication Offset = 65
```

---

Every Replica also maintains its own offset.

Example:

```text
Primary

Offset = 75

Replica 1

Offset = 75

Replica 2

Offset = 68
```

Replica 2 is simply

```
7 Bytes Behind
```

The Replica with the highest offset is always the most up-to-date.

---

# Why Bytes?

Using byte offsets provides several advantages.

- Exact resume point after failures.
- Precise measurement of replication lag.
- Works even if a command is only partially transmitted.
- Independent of command size.

The replication stream is fundamentally just a stream of bytes over TCP.

Redis simply tracks its position within that stream.

---

# Temporary Network Failure

Suppose a Replica disconnects.

```text
12:00

Connected

↓

12:05

Network Failure

↓

12:05:10

Reconnect
```

During those ten seconds,

the Primary continues processing writes.

Question.

Should Redis now send

the entire dataset again?

That would be extremely wasteful.

---

# First Idea

Store every command forever.

```text
SET A

SET B

SET C

...

Millions of Commands
```

Problem.

Memory usage keeps increasing forever.

Clearly impossible.

---

# Replication Backlog

Redis instead stores only **recent replication data**.

Think of it as a circular buffer.

```text
+-------------------------------------------+

Recent Replication Stream

+-------------------------------------------+

Old Entries ← Overwritten ← New Entries
```

Suppose its size is

```
100 MB
```

Only the latest

```
100 MB
```

of replication data is retained.

Older replication data is automatically overwritten.

---

# Partial Synchronization (PSYNC)

Replica reconnects.

It says:

> "I already received everything until Offset 500000."

Primary checks.

Do I still have replication data after Offset 500000?

---

## Case 1

Yes.

Primary sends only the missing bytes.

```text
Replica

↓

Offset = 500000

↓

Primary Sends

500001

↓

Current Offset
```

No full synchronization required.

This is called

**Partial Synchronization (PSYNC).**

---

## Case 2

No.

The missing replication data has already been overwritten.

Now Redis has no option except

**Full Synchronization.**

---

# Choosing Replication Backlog Size

Many beginners think backlog size should depend on

```
Database Size
```

Actually,

it depends on

```
Write Throughput

×

Expected Disconnect Duration
```

Example.

Write Rate

```
20 MB/sec
```

Expected Network Failure

```
30 Seconds
```

Minimum backlog

```
20 × 30

=

600 MB
```

This allows a Replica disconnected for thirty seconds to perform a Partial Synchronization.

---

# Full Synchronization

Suppose the Replica remained disconnected

for

```
3 Hours
```

The backlog no longer contains the missing writes.

Primary must send

the complete dataset again.

```text
Primary

↓

Entire Dataset

↓

Replica
```

This is expensive,

but acceptable,

because such situations should be rare.

Distributed systems generally optimize for the common case,

not exceptional failures.

---

# How Should Full Synchronization Work?

Suppose Redis stores

```
500 GB
```

Should Redis pause client requests,

copy the data,

and then continue serving traffic?

Absolutely not.

The application would remain unavailable for several minutes.

Instead,

Redis performs:

```text
Replica Requests Full Sync

↓

Primary Creates Snapshot

↓

Clients Continue Sending Writes

↓

Snapshot Sent

↓

Remaining Writes Sent

↓

Replica Catches Up
```

Now another question appears.

Where are those new writes stored while the snapshot is being transferred?

The answer:

The **Replication Backlog**.

The backlog serves two purposes.

1. Partial Synchronization.
2. Storing writes during Full Synchronization.

One mechanism solves both problems.

---

# Sentinel

Replication improves availability,

but introduces another problem.

Suppose we have

```text
Primary

↓

Replica 1

↓

Replica 2
```

Primary crashes.

Who decides

which Replica becomes the new Primary?

Certainly not the application.

Redis introduces another distributed component.

**Redis Sentinel**

---

# What is Sentinel?

Sentinel is **not Redis.**

It is a separate process.

Its responsibilities are:

- Monitor Redis nodes.
- Detect failures.
- Elect a Leader Sentinel.
- Promote a Replica.
- Inform applications about the new Primary.

Sentinel does **not** store cache.

It only coordinates failover.

---

# Single Sentinel Problem

One Sentinel creates another SPOF.

```text
Sentinel

↓

Crash
```

Now nobody can perform failover.

Therefore,

multiple Sentinels are deployed.

```text
Sentinel 1

Sentinel 2

Sentinel 3
```

---

# SDOWN

Suppose

Sentinel 1

cannot reach the Primary.

Should it immediately declare

Primary Dead?

No.

Maybe only Sentinel 1 has a network issue.

This state is called

**Subjectively Down (SDOWN).**

Meaning:

> "I think the Primary is unavailable."

Not

"The Primary is definitely dead."

---

# ODOWN

Now Sentinels communicate.

Suppose

```text
S1

Down

S2

Down

S3

Down
```

Everyone agrees.

Now the Primary is

**Objectively Down (ODOWN).**

Only after ODOWN

does failover begin.

---

# Quorum

A majority is required.

Why?

Suppose

```text
S1

Cannot Reach Primary

S2

Can Reach

S3

Can Reach
```

If one Sentinel alone could trigger failover,

temporary network failures would constantly create new Primaries.

Majority voting prevents false failovers.

---

# Leader Election

Once everyone agrees the Primary is dead,

another question appears.

Who performs the failover?

If every Sentinel promotes a Replica simultaneously,

chaos occurs.

Instead,

Sentinels first elect

one Leader Sentinel.

Only that Leader performs failover.

---

# How is the Leader Elected?

Every Sentinel waits for a randomized timeout.

Example.

```text
S1

120 ms

S2

180 ms

S3

250 ms
```

Whoever times out first

requests votes.

Each Sentinel votes only once.

If a Sentinel receives a vote request

before voting for someone else,

it grants its vote.

Suppose

```text
S1

Votes S1

S2

Votes S1

S3

Votes S1
```

S1 becomes Leader.

Notice.

The voting isn't random.

Only the election timeout is randomized.

This prevents all Sentinels from starting elections simultaneously.

---

# Choosing the New Primary

Once a Leader Sentinel exists,

the other Sentinels stop participating.

Only the Leader chooses

the Replica to promote.

Selection is deterministic.

Redis primarily considers:

- Replication Offset
- Replica Priority
- Run ID (Final Tie Breaker)

---

## Replication Offset

The most up-to-date Replica is preferred.

Example.

```text
Replica A

Offset = 1000

Replica B

Offset = 980
```

Replica A contains more recent data.

It wins.

---

## Replica Priority

If two Replicas have identical offsets,

Redis compares

Replica Priority.

Lower priority values are preferred.

Priority

```
0
```

means

never promote this Replica.

---

## Run ID

Suppose everything is identical.

Offsets match.

Priorities match.

Redis still needs one deterministic answer.

Every Redis instance has a unique

Run ID.

Redis finally compares Run IDs,

ensuring every Sentinel independently reaches exactly the same decision.

No randomness is involved.

---

# fork() and Copy-on-Write (CoW)

During Full Synchronization,

Redis needs to create an RDB Snapshot.

Question.

Should Redis copy

500 GB

before serving clients?

Impossible.

Redis would become unavailable.

Instead,

Redis calls

```
fork()
```

provided by Linux.

The operating system creates a Child Process.

Initially,

both Parent and Child share the same memory.

Nothing is copied immediately.

---

Suppose

Parent modifies

one memory page.

Linux notices.

Instead of changing the shared page,

Linux:

1. Creates a new page.
2. Copies only that page.
3. Parent modifies the new page.
4. Child continues reading the original page.

Only modified pages are copied.

This is called

**Copy-on-Write (CoW).**

---

# Why is Copy-on-Write Brilliant?

Without CoW,

Redis would immediately copy hundreds of gigabytes.

With CoW,

Redis continues serving client requests,

while the Child Process creates the snapshot.

The snapshot represents a perfectly consistent view of memory

at the instant fork() occurred.

---

# Memory Tradeoff

Copy-on-Write isn't free.

Suppose Redis stores

```
500 GB
```

Immediately after fork(),

the application updates almost every key.

Linux now copies almost every memory page.

Memory usage may temporarily approach

```
500 GB

+

500 GB

≈

1 TB
```

This temporary memory increase is an important production consideration.

# Key Takeaways

Redis exists because application-level caching doesn't scale.

Redis stores data primarily in RAM to achieve extremely low latency.

Persistence protects Redis from crashes.

Replication provides High Availability and Read Scaling.

Replication Offset tracks progress using bytes rather than commands.

Replication Backlog enables Partial Synchronization.

Sentinel performs monitoring, leader election and failover.

Only one Leader Sentinel performs failover.

Replica selection is deterministic using Replication Offset, Priority and Run ID.

fork() and Copy-on-Write allow Redis to create snapshots while continuing to serve clients.
